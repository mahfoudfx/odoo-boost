# Research: keeping routine Odoo agent tasks small

Reviewed 2026-09-24. This is a design input, not a proposed package change. It compares public source material with the reported translation-edit trace; it does not independently validate that trace or benchmark a model.

## Findings

1. **A larger skill catalog is unlikely to solve excessive exploration by itself.** Agent Skills expose every installed skill's name and description at discovery time, then load the selected `SKILL.md` and optional references. Clear, narrow triggers and small root files matter. Google recommends focused skills, brief descriptions, and scripts whose source need not be read for each run; OpenAI warns that too many or overlapping skills can cause inappropriate activation and excessive context. [Agent Skills overview](https://agentskills.io/home), [Antigravity skill guidance](https://www.antigravity.google/docs/skills?tab=ide), [OpenAI guidance on skill and prompt bloat](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).

2. **The proposed `unclecatvn/agent-skills` project is maintained, but its main workflow is a poor default for tiny edits.** Its README describes 10 packs, four version-specific Odoo reference packs, three specialized agents, tests, and a CI security scan. Its latest visible release, v1.0.14, documents Odoo 16–19 coding-guideline updates. These are useful maintenance signals, not proof of task efficiency or correctness. The `odoo-workflow` skill explicitly triggers for *any* Odoo Python/XML change, asks for version resolution, source-chain tracing and a cited Context Brief before code, then install/test/i18n/review steps. Its Odoo 18 index also tells users to run this workflow before coding. That policy could add many steps to a PO-file label fix, a local view rearrangement, or a simple field label edit. It does include good ideas such as bounded reading (120 lines per hop, three hops) and reading only the needed reference. [Repository README](https://github.com/unclecatvn/agent-skills), [v1.0.14 release](https://github.com/unclecatvn/agent-skills/releases/tag/v1.0.14), [workflow source](https://raw.githubusercontent.com/unclecatvn/agent-skills/main/skills/odoo-workflow/SKILL.md), [Odoo 18 skill index](https://raw.githubusercontent.com/unclecatvn/agent-skills/main/skills/odoo-18.0/SKILL.md).

3. **Packaging details matter.** The project says its CLI and skills installer copy selected packs, while agents and rules require separate routes; its Antigravity CLI route copies a pack to `.shared/skills/` and a `.agent/workflows/skills.md` pointer, and the README explicitly says this does not guarantee native skill discovery. Current Antigravity documentation instead lists workspace `.agents/skills/<skill>/` as the native location and plugin skill folders for CLI. Antigravity IDE workflows are scheduled for deprecation on 2026-11-01. If borrowing from this repository, inspect and adapt individual reference files or instructions; do not assume its installer is the right distribution path for odoo-boost. [Project installation notes](https://github.com/unclecatvn/agent-skills), [Antigravity skill locations](https://www.antigravity.google/docs/skills?tab=ide), [workflow migration notice](https://www.antigravity.google/docs/ide/workflows/).

4. **Persistent rules are suitable for a short decision boundary, not a full procedure.** Antigravity loads `AGENTS.md`/`GEMINI.md` and scoped rules as context; OpenAI's published guidance specifically flags mandatory document reading before every edit as excessive for typo fixes. A compact shared rule could say: start with a local search, change the smallest relevant files, run one proportional check, and expand investigation only on ambiguity, failure, or behavior risk. A skill can hold specialized Odoo recipes on demand. [Antigravity rules](https://antigravity.google/docs/rules/), [OpenAI guidance](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), [Claude Code skills versus persistent context](https://code.claude.com/docs/en/skills).

5. **Separate task complexity from file type.** The same XML file can contain a one-word label edit or a risky inherited-view change. A proposed triage is: routine local edit (known target and behavior), bounded feature (new field, smart button, kanban card, view rearrangement), and investigation (unclear cause, cross-module behavior, security/data migration). The first gets a short search/edit/check loop; the second gets targeted model/view/version checks and affected tests; the third may need source tracing or a specialist agent. This is a design inference, consistent with Antigravity's advice to keep skills focused and match decision trees to complex work. [Antigravity skill guidance](https://www.antigravity.google/docs/skills?tab=ide).

6. **Tooling should be deterministic and output-light where possible.** Small scripts can validate PO syntax, find duplicate or missing source strings, identify module/view targets, or select relevant checks. Give the agent a concise result, not a full source dump. This aligns with Google's guidance to use scripts for deterministic tasks and treat them as black boxes. An MCP tool is justified only if it exposes data or capability a local script cannot provide conveniently; an extra tool does not by itself change the model's choice to over-investigate. [Gemini CLI skill best practices](https://geminicli.com/docs/cli/skills-best-practices/), [Antigravity skill guidance](https://www.antigravity.google/docs/skills?tab=ide), [OpenAI on skills and MCP roles](https://developers.openai.com/plugins/concepts/skills).

7. **Measure before adding a strict cap.** A hard six-call limit is easy to violate on legitimate Odoo changes and can encourage premature completion. Instead, evaluate representative tasks with and without a short rule or skill: success/correctness, wall time, total input/output tokens, tool calls, files read, unnecessary core-source reads, repeated reads, and compaction. Include near-miss cases that must trigger deeper checks (for example a translated report header produced dynamically, a smart button with access-right implications, or a view anchor from another module). OpenAI recommends trace and dataset evaluation for workflow changes. Antigravity's headless JSON output exposes token counts, and its status-line schema exposes context usage for local observation. [OpenAI agent evals](https://developers.openai.com/api/docs/guides/agent-evals), [Antigravity headless output](https://www.antigravity.google/docs/cli/headless/), [Antigravity status line](https://www.antigravity.google/docs/cli/statusline/).

## Suggested collection policy

Use official Odoo documentation and actual project source as factual references when required. Treat community skills as **candidate procedures**, reviewed file by file. Before installing any third-party skill, inspect its `SKILL.md`, references, scripts, activation description, and any shell commands; pin a reviewed revision if adopted. A CI scan and release cadence do not replace that review. Google's skill guidance explicitly recommends reviewing third-party skills before installation. [Gemini CLI skill security guidance](https://geminicli.com/docs/cli/skills-best-practices/), [unclecatvn test and scan claims](https://github.com/unclecatvn/agent-skills).

The best next experiment is a small routine-change policy plus one focused Odoo translation recipe, benchmarked against the reported translation task and several broader simple tasks. Keep code-review, deep tracing, and planning skills available for tasks that call for them, without making them mandatory for every edit.
