# Workflow Evaluation

Use the same prompts against the installed agent instructions after each router or skill change. Compare the agent's actions and result, not a fixed tool-call target. Model-side token counts depend on the client and are not directly controlled by Odoo Boost. Keep the client, model, task fixture, and starting repository state fixed within each comparison; run fresh and long-context sessions separately.

| Prompt | Expected route and completion evidence |
|---|---|
| Rename a label in an existing inherited form view | Low: identify the exact record and XPath, edit, parse XML, review diff; no live upgrade |
| Translate static Section 5 report column titles in French and Arabic PO files | Low: identify the source text and matching references, edit requested catalogs, validate PO syntax and coverage, review diff; no core translation-engine trace |
| Rearrange existing form or list fields | Low: identify the view and inheritance anchor, move the existing nodes, parse XML, review diff |
| Adjust an existing kanban card's layout using existing fields | Low: inspect the card template and field references, edit, parse XML, review diff |
| Change static QWeb report formatting | Low: edit the matching template nodes, parse XML, review diff |
| Add a simple search filter for an existing field | Low when the domain and intended records are clear; check the domain and XML, review diff |
| Fix a local compute method when its recordset is empty | Low if bounded: inspect dependencies and callers, edit, run a focused behavior check |
| Add a stored field to an existing model and show it in a view | Medium: check the model extension, imports, relevant data order, field reference, existing-data/default implications, access, and focused behavior |
| Add a smart button that opens related records | Medium: check action, domain, count, model, and the records each user may access |
| Translate a report header assembled dynamically | Escalate: locate how the text is built and extracted before editing catalogs |
| Move a field using an anchor from an uncertain inherited view | Escalate: resolve the inheritance order and anchor before editing |
| Make an existing field required with stored rows | Escalate: account for existing data and the upgrade path |
| Add a smart button whose target has restrictive record rules | Escalate: verify allowed and denied visibility for both count and opened records |
| Restrict a public download controller | High: inspect authentication and access path, verify allowed and denied cases |
| Migrate an addon across Odoo versions | High: verify target-version APIs and views, data migration risks, and affected tests |
| Deadline: fix a local compute method | Same correctness evidence as the compute case, with narrower exploration and a brief result |

Record for each run: correct result and first-pass completion; selected scope; files and skills opened; specialist-agent handoffs; repeated calls and reads; unrelated upstream-core reads; checks performed; elapsed time; input, output, and cached tokens when the client reports them; and compactions. Record the reason for broadening a search or running a full suite. Compare a baseline generated by the previous release with the current generated instructions in the same client/model. The improvement goal is fewer irrelevant reads and shorter completion time without more first-pass failures or missed escalations.

The listed cases are examples, not a closed classifier. A new task takes the routine path when its target and intended result are precise, it preserves access and stored data meaning, and a focused check covers its likely failure. Use a bounded or deep path when a specific dependency or risk crosses that boundary. For routine cases, an unexplained broad source scan, repeated verification, or agent handoff is a workflow failure even when the final edit is correct.

The package test suite verifies generated text, installation, and server behavior. It cannot establish model obedience or client-side prompt token counts; those require runs in the target agent clients.

## Offline documentation check

Compare the same version-specific developer, administration, and application
questions using a local docs index and the client's normal online lookup.
Record lookup latency, returned characters, client input tokens, any web-search
charge reported by that provider, answer correctness, and source version. Also
run a routine local edit that needs no documentation: it should perform no docs
lookup. Keep the offline route only if its targeted excerpts reduce cost or
latency without degrading answers; package tests alone cannot prove that.
