# Workflow Evaluation

Use the same prompts against the installed agent instructions after each router change. Compare the agent's actions and result, not a fixed tool-call target. Model-side token counts depend on the client and are not directly controlled by Odoo Boost.

| Prompt | Expected route and completion evidence |
|---|---|
| Rename a label in an existing inherited form view | Low: identify the exact record and XPath, edit, parse XML, review diff; no live upgrade |
| Fix a local compute method when its recordset is empty | Low if bounded: inspect dependencies and callers, edit, run a focused behavior check |
| Add a stored field shown in a view | Medium: check imports, manifest/data order, field reference, access implications, and focused behavior |
| Restrict a public download controller | High: inspect authentication and access path, verify allowed and denied cases |
| Migrate an addon across Odoo versions | High: verify target-version APIs and views, data migration risks, and affected tests |
| Deadline: fix a local compute method | Same correctness evidence as the compute case, with narrower exploration and a brief result |

Record for each run: selected scope, files and skills opened, repeated calls, checks performed, whether the code works on first pass, and any missed dependency. Compare a baseline generated by the previous release with the current generated instructions in the same client/model. The improvement goal is fewer irrelevant reads and shorter completion time without more first-pass failures. Broadening a search or running a full suite needs a named risk or failed focused check.

The package test suite verifies generated text, installation, and server behavior. It cannot establish model obedience or client-side prompt token counts; those require runs in the target agent clients.
